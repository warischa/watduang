# 06 — Prototype: หน้าตั้งผู้เล่น + จังหวะส่งมือถือวนกัน

Type: prototype
Status: resolved
Blocked by: —

## Question

ส่วนนี้ผู้เล่นเจอทุกครั้งก่อนเข้าทุกเกม ถ้าพัง เว็บพังหมด — และเป็นเรื่องที่ถกด้วยคำพูดไม่จบ ต้องทำของจริงมาจิ้ม

ตอบด้วย prototype ที่กดเล่นได้จริงบนมือถือ:

1. ตั้งชื่อผู้เล่น 2-10 คนยังไงให้ไม่น่าเบื่อ — พิมพ์ทีละคน? เลือกจำนวนแล้วใช้ชื่อ default? จำจากครั้งก่อน (localStorage) แล้วแก้ทีหลัง?
2. หน้าจอ "ส่งมือถือให้คนถัดไป" หน้าตายังไง — กันคนเห็นของคนอื่น, กันกดพลาด, อ่านออกในที่แสงน้อยและเสียงดัง
3. ปุ่มใหญ่แค่ไหนถึงกดได้ตอนมือไม่นิ่ง
4. บทลงโทษแสดงยังไงให้เป็นกลางจริง — กลุ่มผู้เล่นตัดสินเองว่าคืออะไร โดยเว็บไม่ต้องบอกใบ้

Prototype นี้เป็นของทิ้ง ไม่ใช่โค้ดชุดจริง เก็บลิงก์ไฟล์ไว้ใน ticket

## Prototype

[`prototypes/06-player-shell.PROTOTYPE.html`](../prototypes/06-player-shell.PROTOTYPE.html) — ไฟล์เดียว ดับเบิลคลิกเปิด ไม่ต้อง build

สลับด้วย `?variant=A|B|C` · ปุ่มลูกศรล่างจอ · หรือลูกศรซ้าย/ขวาบนคีย์บอร์ด · แถบบนสุดโชว์ state ทั้งหมดตลอดเวลา

| | วิธีตั้งผู้เล่น | วิธีเปิดดู |
|---|---|---|
| **A** | พิมพ์ชื่อทีละคน (list) | แตะ |
| **B** | เลือกจำนวน 2-10 ก่อน ชื่อเป็น `คนที่ N` แก้ทีหลัง | **กดค้าง 0.9 วิ** มีวงแหวนวิ่ง |
| **C** | จำคนที่เคยเล่น แตะเลือกว่าคืนนี้ใครอยู่ | ปัดขึ้น |

สามแบบนี้ **ไม่เหมือนกันเชิงโครงสร้าง** — A คือช่องพิมพ์ B คือ number picker C คือ selection grid ไม่ใช่แค่เปลี่ยนสี

### สิ่งที่อยากให้ลองแล้วบอก

1. ตอน 8 คน แบบไหนเริ่มเล่นได้เร็วสุดโดยไม่รำคาญ
2. **กดค้าง (B) กันเปิดพลาดได้จริงไหม หรือกวนตีน** — ข้อนี้ตอบด้วยการพูดไม่ได้ ต้องลองบนมือถือจริงในที่แสงน้อย
3. ปุ่มใหญ่พอไหมตอนมือไม่นิ่ง (ตั้งไว้ 64px)
4. หน้าบทลงโทษเป็นกลางจริงไหม หรืออ่านแล้วยังรู้สึกว่าเว็บกำลังใบ้อะไรอยู่

ฟีดแบ็กที่มีค่าที่สุดมักเป็น *"เอาการตั้งชื่อของ B กับวิธีเปิดของ A"* — นั่นคือดีไซน์จริงที่ต้องการ

### ตรวจแล้ว (รันจริงในเบราว์เซอร์ ไม่ใช่อ่านโค้ด)

- ทั้ง 3 variant เดินครบ flow: setup → ส่งมือถือ → เปิดคำท้า → จบรอบ → บทลงโทษ
- **ไม่มีคำต้องห้ามใน DOM** (เหล้า/เบียร์/แอลกอฮอล/หมดแก้ว = 0)
- **`images=0`** — ตรงกฎเหล็กข้อ 1 ของแผนที่
- **บั๊กที่เจอจากการรัน ไม่ใช่จากการอ่าน:** `localStorage` โยน SecurityError บน `data:` URL ทำให้ `save()` พังเงียบๆ และปุ่ม "เริ่มเล่น" กดแล้วไม่มีอะไรเกิดขึ้น — แก้เป็น try/catch + fallback ใน memory แล้ว **ข้อนี้ต้องยกไปโค้ดจริงด้วย** เพราะโหมดส่วนตัวและเบราว์เซอร์ที่บล็อกคุกกี้โยนแบบเดียวกัน ถ้าไม่กันไว้ เว็บจะตายทั้งหน้าเพราะเรื่องจำชื่อ

## Answer — ผสม C+B สำหรับการตั้งผู้เล่น · กดค้างสำหรับการเปิดดู

### ตั้งผู้เล่น: hybrid ตามสถานะของ roster

```
เปิดหน้าเกม
├─ roster ว่าง (มาครั้งแรก)  → number picker แบบ B  ── เลือก 2-10 → ชื่อ default "คนที่ N" → เริ่มเล่นได้ใน 2 แตะ
│                               └─ แตะชื่อเพื่อแก้ทีหลังได้ ไม่บังคับ
└─ roster มีคน (กลับมาเล่นอีก) → selection grid แบบ C ── แตะเลือกว่าคืนนี้ใครอยู่ → ไม่ต้องพิมพ์เลย
                                 └─ ปุ่ม "เพิ่มคนใหม่" เปิดช่องพิมพ์
```

**ทำไมต้องสองสถานะ ไม่ใช่ตัวเดียว:** C คือจุดต่างแกนกลางตาม [#10](10-front-door-strategy.md) แต่ C ล้วนพังตอนมาครั้งแรกเพราะหน้าว่างเปล่า · B เร็วที่สุดตอนแรกแต่ทิ้ง roster · hybrid แก้ทั้งสองฝั่ง และต้นทุนคือโค้ดเพิ่มไม่กี่สิบบรรทัด

**A ตกไป** — พิมพ์ทีละคน 8 ครั้งทุกครั้งที่เล่น คือ pain ที่ roster ถูกสร้างมาเพื่อแก้พอดี

### เปิดดูคำท้าส่วนตัว: กดค้าง 0.9 วินาที + วงแหวนวิ่ง

กันเปิดพลาดตอนมือไม่นิ่ง และวงแหวนบอกความคืบหน้าทำให้ไม่รู้สึกว่าค้าง · การแตะเฉยๆ นิ้วโดนหน้าจอตอนส่งมือถือ = คนอื่นเห็นคำท้า ซึ่งทำลายเกมทันที

**ไม่กระทบเกม #1 ระเบิดเวลา** — เกมนั้นไม่มีขั้นเปิดดูส่วนตัว ส่งมือถือแล้วมันนับถอยหลังเอง สร้างได้เลยไม่ต้องรอส่วนนี้

### สิ่งที่ต้องยกไปโค้ดจริง ไม่ใช่แค่ดีไซน์

1. **`localStorage` ต้องมี try/catch + fallback ใน memory** — prototype เจอของจริงว่ามันโยน SecurityError บน `data:` URL แล้ว `save()` พังเงียบๆ จนปุ่ม "เริ่มเล่น" กดไม่ติด · โหมดส่วนตัวและเบราว์เซอร์ที่บล็อกคุกกี้โยนแบบเดียวกัน **ถ้าไม่กัน เว็บตายทั้งหน้าเพราะเรื่องจำชื่อ**
2. **ปุ่มหลักไม่ต่ำกว่า 64px** — ตั้งไว้ใน prototype แล้ว
3. **โทนสีเข้ม คอนทราสต์สูง** — เล่นในที่แสงน้อยเป็นสถานการณ์ปกติของเว็บนี้ ไม่ใช่ edge case

### ของทิ้ง

`prototypes/06-player-shell.PROTOTYPE.html` เก็บไว้เป็น primary source ของการตัดสินใจนี้ **ห้ามยกโค้ดไปใช้ตรงๆ** — เขียนใหม่ภายใต้เงื่อนไขโค้ดจริง (TypeScript, แยก shell เป็น component, มี test)

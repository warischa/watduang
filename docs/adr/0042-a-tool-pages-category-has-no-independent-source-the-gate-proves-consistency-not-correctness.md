# ADR-0042 — a tool page's category has no independent source; the gate proves consistency, not correctness

Date: 2026-08-26 · Status: accepted · Extends ADR-0030, ADR-0032

## Context

`scripts/crawl-check-gamenav.mjs` is the CI gate that proves each page's `<GameNav>` block renders the
sibling links its category implies. For a game page, the expected category comes from
`src/games/manifest.ts` — a source independent of the rendered page. For a tool page, it does not:
the `toolPages` map in `crawl-check-gamenav.mjs` reads the expected category off `category="([^"]+)"`
matched out of the page's own `<GameNav ... />` source. The comment above that same map already names
this: the value the gate checks *against* is the same value the page under test declares, so a tool
page whose category is wrong but self-consistent — copy-pasted from the wrong sibling — renders from
that value, is expected from that value, and passes green.

This is exactly the shape ADR-0030 (a fixture must not be sourced from the artifact it tests) names.
The difference here is that ADR-0030's version was fixable; this one is not, because no independent
source exists for a tool page's category:

- The `categories` export in `src/games/categories.ts` is `Record<Category, CategoryMeta>`, keyed by
  the hand-written game union (each entry carries its own `carriesGroup` flag). A tool is not a game
  and has no entry.
- The comment above `toolsGroup` in `src/tools/manifest.ts` explains why: the tools group is
  deliberately not a category, and adding a third key there "would make every game's category check
  accept a value no game can hold." That is ADR-0032's decision, not an oversight — ADR-0032 keeps the
  category union hand-written and keyed by games alone, specifically to keep the `validate-games.mjs`
  prebuild gate cheap and safe.
- The sitemap is generated by the `sitemap()` integration in `astro.config.mjs` from built page URLs;
  the only gate that reads it checks URL presence per tool slug (`sitemap-tool-pages-check` in
  `package.json`), not category.
- `public/staticwebapp.config.json` and `public/robots.txt` carry routes and headers, not categories.
- There is no content collection and no frontmatter (`src/content/` does not exist) and no route
  config beyond `src/pages/` that could carry a category value.
- The only other place a tool page's category is stated is the same `<GameNav category="party">`
  literal the gate already reads — same page, so not independent by definition.

A previous session recorded this exposure without closing it. This ADR is the closure: not a fix, an
acceptance, because a fix would require reversing ADR-0032.

## Decision

**The limit is accepted, not closed.** `crawl-check-gamenav.mjs` keeps proving what it can prove for
tool pages — that the declared category and the rendered sibling count/scoping agree with each other
and with the independent games manifest — and keeps NOT proving that the declared category is the
editorially correct one. No tools-category manifest gets invented to satisfy this gate; doing so would
fight the decision ADR-0032 made on purpose.

## What the gate does and does not prove

- **Proves:** for a tool page, whatever category it declares in `<GameNav category="...">`, the
  rendered nav block scopes to that category's actual games (the `expected` field in that same
  `toolPages` map cross-checks the declared value against `src/games/manifest.ts` and
  `src/games/categories.ts`, both independent of the tool page itself).
- **Does not prove:** that the declared category is the right one for that tool page. A wrong-but-
  self-consistent value — `party` copy-pasted onto a page that should say something else once a second
  category exists for tools — passes with no red anywhere in CI.

Today all four tool pages declare `category="party"` and there is only one category a tool page could
plausibly carry, which is why this gap has not yet produced a real defect. The risk is latent, not
active.

## The fact that would reverse this

A tool page's category gaining an independent home — a manifest entry, frontmatter field, or any
record not derived from the page's own `<GameNav>` props — would give this gate something to check
against and close the gap the same way it is already closed for games. That would require amending
ADR-0032, which deliberately keeps tools out of the category manifest. Absent that amendment, or absent
a second tool category ever existing, this ADR stands.

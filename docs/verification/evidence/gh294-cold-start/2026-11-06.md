# gh#294 — feedback endpoint cold start, 2026-11-06

Function App `func-watduang-feedback` (Windows Consumption, `rg-watduang`), 64-bit, Node `~24`. Every POST went to
`/api/feedback` on the SWA default hostname, with fields `kind=feedback` and `message`. Each message was tagged
"[gh#294 test]". Rows were read back from `feedback-2026-11.csv` with `az storage blob download --auth-mode login`.

## The failure

| When | Result |
|---|---|
| 06:24:01 UTC, about 50 min after the app's last shutdown (event log: shutdown 05:32:24) | **500** after 45.3s, body `Backend call failure`, no row written |
| the next request | 303 `/feedback/sent/` after 7.4s, one row written |

`Backend call failure` is the SWA `/api` proxy's own answer, so the proxy gives up at about 45s. The function's cold
start took longer than that. The request that timed out never wrote its row.

## State before the fix

- No `WEBSITE_RUN_FROM_PACKAGE` setting. `site/wwwroot` held the extracted app, and its `node_modules` is 82 MB in
  9,659 files (2,504 of them `.js`/`.mjs`/`.cjs`; counted from a local `npm ci --omit=dev` of the same lockfile).
- There is no Application Insights resource. Host file logs exist only for 2026-11-04, because file logging runs only
  while debugging. `LogFiles/eventlog.xml`, read through the Kudu VFS API, records each start and shutdown.
- A local `func start` loop did not reproduce the failure. The local worker initializes before the first request,
  and the 17s it measured came from storage retries against a dummy URL.

## Experiment 1: run from package (owner approved, 2026-11-06)

`WEBSITE_RUN_FROM_PACKAGE=1`, then `config-zip` of the unchanged source (`services/feedback` has 0 changes since
`786ee65`; 16.6 MB zip, 10,508 entries) with ADR-0074's deploy command. The package landed in `data/SitePackages`.

| Probe | Result | Valid? |
|---|---|---|
| first POST after the deploy (host started 06:28:23) | 303 after 8.3s, row written | yes, n=1 |
| second POST | 303 after 0.34s | yes |
| POSTs after `az functionapp restart`, twice | 303 after about 0.3s | **no**: the restart returned before it recycled the worker, so these were not cold starts |
| POST after 25 idle minutes (06:53:55) | 303 after 1.9s | **no**: the event log shows no shutdown after 06:28:47, so the app may not have been cold |

Revert: delete the setting and `config-zip` the same source (the code is unchanged, so the same zip serves).

## Still open

The deciding probe is a POST after at least 40 untouched minutes. It counts only if `eventlog.xml` shows a
`FUNC-WATDUANG-FEEDBACK ... has shutdown` event between the last touch and the POST.
